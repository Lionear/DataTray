Open, and genuinely undecided.
  • Layout algorithm. Everything above assumes a layered left-to-right layout, hand-placed here. Whether that comes from ~150 lines of our own topological layering, a force-directed pass, or a NuGet graph library is the one decision with real consequences — a library means a dependency inside a plugin.
  • Can boxes be dragged? Every serious tool lets you nudge a table and remembers it. That means persisting positions per connection+schema, which is a chunk of work the mockup quietly assumes away.
  • Where does it open? Drawn here as a tool window. It could equally be a tab in the main window, beside a query tab — better for keeping it open while you work, more host plumbing.
  • Engine coverage. Shared.Schema reads postgres, mysql, sqlserver and sqlite. Mongo, Redis, ClickHouse and DuckDB get nothing — the menu entry should be absent there rather than opening an empty canvas.

Phase 2 — editing (Model A: edit against the live schema)

The diagram is the database. Edits never touch it directly — they accumulate as pending changes and become a migration script you read and run yourself. Every operation below already exists as a SchemaChange; AlterScriptWriter renders them per engine.

5 · Review. The pending changes rendered to DDL for this engine. Nothing has run — the script goes to a query tab, where you read it and decide. Ordering is the substance here: the table is created before the key that references it.

Review changes · Demo shop · PostgreSQL 16 
-- 4 changes · generated for PostgreSQL · nothing has been executed

CREATE TABLE public.wishlists (
    id          integer GENERATED BY DEFAULT AS IDENTITY,
    customer_id integer NOT NULL,
    name        text NOT NULL,
    created_at  timestamp NOT NULL DEFAULT now(),
    CONSTRAINT wishlists_pkey PRIMARY KEY (id)
);

ALTER TABLE public.orders ADD COLUMN coupon_code text;

-- after the table exists, not before
ALTER TABLE public.wishlists
    ADD CONSTRAINT wishlists_customer_id_fkey
    FOREIGN KEY (customer_id) REFERENCES public.customers (id);
3 statements
Why it stops here. Transactional DDL exists in PostgreSQL and SQL Server, but not in MySQL — there a half-failed migration leaves a half-changed table and no way back. Handing over a script keeps that decision, and its blast radius, with the person who owns the database. Running it from the diagram is a later refinement, once generated scripts have earned trust.

6 · An edit the engine cannot express. The same relation drawn on a SQLite connection. SQLite cannot add a foreign key to an existing table, and the dialect already says so — so the edit is refused where it is made, rather than generating a silent table rebuild.

Still open in Phase 2.
  • The column-type editor. Drawn here as free text with the type on the right. A curated per-engine pick-list is friendlier and considerably more work — SqlDialect.ColumnSpec knows how to write a type, not how to offer one. Free text with validation is the cheap route and can be tightened later.
  • Composite foreign keys. ForeignKeyDef carries column lists, so multi-column keys must be expressible. Dragging one pair at a time and extending the pending edge is the likely answer; the mockup shows only the single-column case.
  • Drop and rename. Both exist as SchemaChange and neither is drawn above. Dropping a table that others reference needs its incoming keys dropped first — the same ordering problem as state 5, in the harder direction.
